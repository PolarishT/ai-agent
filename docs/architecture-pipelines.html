离线 / 在线链路技术文档

深入剖析服务端两条核心链路：离线链路把商品与文档可靠地索引进知识库（PostgreSQL + Milvus），在线链路用 StateGraph 编排的多轮 Agent 把用户一句话变成带商品卡片的流式导购回答。所有描述均对应当前实现代码。

Spring Modulith Alibaba StateGraph Spring AI RAG Spring Statemachine RocketMQ Outbox Milvus 混合检索 SSE 流式

两链路的交汇点

离线链路写出的 rag_chunks（PostgreSQL 行 + Milvus 向量）正是在线链路检索读取的对象。两者通过索引代际（index generation）对齐：只有 COMMIT 后的"活跃代"才会进入在线回答，避免半提交向量污染结果。

Part A · Offline

A 离线链路 · 索引

目标：把"商品 JSON / 文档"可靠、可重试、可观测地转成"可被语义+关键词检索的 chunk"。强调事务一致性（Outbox）、可恢复（状态机 + 对账）与零半提交（代际提交）。

A.2 两条数据入口

① 文档入口

POST /public/rag/documents/create（JSON 或 multipart 文件）。

document 模块落库 rag_documents，并在同一事务内发布 DocumentIndexRequestedEvent。删除/重建走 DocumentIndexCleanupRequestedEvent。

② 商品入口

POST /admin/catalog/import（批量草稿）与 /admin/catalog/import/json（外部 snake_case 资料）。

事务化写入 catalog_product / catalog_sku / catalog_product_knowledge / catalog_product_faq / catalog_product_review，渲染商品 Markdown，双写 rag_documents（source_type=catalog-spu 等），再触发离线索引。

两条入口最终都汇入同一条索引流水线。商品与既有 Markdown 文档在同一 rag_documents / rag_chunks 表内混合存放，互不影响。

A.3 模块间事件解耦

document 不直接调用 indexing，而是发事件——这是 Spring Modulith 的边界纪律。

indexing/application/IndexingDocumentEventListener
@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)
void onDocumentIndexRequested(DocumentIndexRequestedEvent event) {
    indexingCommandFacade.enqueue(...);   // 登记索引作业 + Outbox
}

使用 BEFORE_COMMIT 阶段监听：业务写入与"索引作业登记 / Outbox 行"在同一个数据库事务内提交，从根上杜绝"业务落库成功、索引丢失"的不一致。

A.4 索引状态机

每个文档的索引进度由 Spring Statemachine 驱动（IndexWorkflowStateMachineFactory），状态与跃迁全程审计到 rag_index_job_transitions，因此任意时刻都能回答"这篇文档卡在哪一步"。

另有两个终态：FAILED（不可恢复或重试耗尽）与 SKIPPED（内容哈希未变化，无需重复索引）。状态机的"幂等性"由内容 shortSha + 索引代际共同保证：重复提交同一内容会被 SKIP。

A.5 Outbox 可靠投递

跨进程异步严格按优先级选型：RocketMQ（含 Outbox）> Reactor 阻塞调度 > @Async 虚拟线程。索引派发用的就是最高级的 Outbox 模式。

1
事务内写 Outbox 行业务写入与 rag_index_outbox 登记同一事务提交（PENDING）
2
定时派发RagIndexOutboxDispatcher 按 rag.outbox.dispatch-fixed-delay-millis 扫描 PENDING，发往 RocketMQ，置 SENDING
3
消费执行RagIndexMessageListener 收到消息 → RagIndexingService 跑状态机流水线
✓
幂等收敛成功置 SENT；超时(sending-stale-millis)的 SENDING 行由对账重投，重复消息因代际/哈希被 SKIP

当 rag.rocketmq.enabled=false 时，RagDirectIndexEventPublisher 在进程内直接驱动流水线——同一套状态机，省去 MQ 依赖，便于本地与最小化部署。

A.6 切块与 chunkType 归类

RagTextChunker 按 rag.chunk-size=400 / rag.chunk-overlap=80 切块。商品文档经 ProductChunkTypeNormalizer 启发式归类 chunkType（如 TITLE / DESC / ATTR 等），普通 Markdown 文档统一归 BODY。

为什么要分类型

chunkType 是在线检索的"路由依据"：检索阶段会按意图把召回下推到特定 chunkType（如详情类问题优先 ATTR/DESC，标题命中权重更高），显著提升商品场景的召回精度。详见 B.6 混合检索内核。

A.7 向量化与代际提交

RagMilvusVectorIndexer 用 Doubao 多模态 Embedding 把每个 chunk 向量化，写入 Milvus collection rag_chunks，每条向量携带 indexGeneration 与 vectorId。

A
写新代际本次索引产出的向量标记为新的 generation，与旧代际并存
⎇
COMMIT 切换全部写成功后，原子地把"活跃代际"指向新代
✓
在线只读活跃代检索回查 findSearchableByVectorIds 时只对齐活跃代际，半提交向量永不进入回答
维度一致性

Embedding 维度必须与 Milvus collection 维度一致（如 Doubao 2048），否则写入"成功"但检索报错。这是部署期最常见的坑（见部署文档 §4.3）。

机制组件职责

重试金字塔

与在线检索的"快速失败"相反，离线索引把"重试"做厚——四级递进，确保每篇文档最终一定被索引成功，或被明确标记为终态失败。

① 尝试级进程内退避重试
→
② 消息级RocketMQ 重投
→
③ Outbox 级滞留重投
→
④ 对账级兜底重驱
层级机制配置 / 触发
① 尝试级单次索引失败的进程内重试 + 退避rag.indexing.max-retries=3 · retry-backoff-millis
② 消息级RocketMQ 消费失败自动重投rag.rocketmq.max-attempt-times=3
③ Outbox 级处于 SENDING 但滞留的派发行重新投递rag.outbox.sending-stale-millis · retry-backoff-millis
④ 对账级卡住作业重驱、终态 FAILED 退避后再试RagIndexRecoveryTask：processing/pending-stale-millis · failed-retry-millis（默认 1h）

失败是否值得重试由 RagIndexingFailureClassifier 判定：可重试异常进入退避重试，不可重试或达到 max-retries 则落终态 FAILED 并按需邮件告警。重复消息因内容哈希 + 索引代际被 SKIP，重试天然幂等（见 A.7）。

Part B · Online

B 在线链路 · Agent 编排

目标：把用户一句自然语言，经"意图识别 → 任务规划 → 子图执行（检索/购物车/下单）→ 流式答案"变成带商品卡片的导购回复。核心是一张用 Spring AI Alibaba StateGraph 编排的主图，按意图路由到各业务子图。

B.2 SSE 入口与事件协议

唯一在线入口：GET /api/v1/public/agent/turn，返回 text/event-stream。

参数必填说明
userId / conversationId是用户与会话标识（多轮记忆键）
message是用户本轮自然语言（≤2000）
requestId否幂等键，缺省自动生成 UUID
imageRef否多模态图片引用（预留）
streamMode否prod（默认，精简事件）/ trace（全量节点事件，调试用）

事件类型（AgentStreamEventType）

事件prod 暴露含义
turn.started✅回合开始（turnId / requestId / conversationId）
workflow.started✅意图判定完成，目标 workflow 选定
node.started仅 trace子图节点开始
node.completed仅 trace子图节点完成
node.failed仅 trace子图节点失败
answer.delta✅答案 token 流式片段
answer.completed✅答案落库完成（messageId）
turn.completed✅回合收尾（status / intent / targetWorkflow）
error✅不可恢复错误（白名单化文案 + recoverable 标记）
prod vs trace

生产模式只下发面向用户体验的事件子集（开气泡、流式追加、收尾）；streamMode=trace 会原样下发每个图节点的 started/completed/failed——演示与排障时能直观看到 Agent "走了哪条路"。

限流保护

该入口标注了注解式限流 @RateLimit（common.ratelimit AOP 切面），按「userId:conversationId」维度计数（1min ≤ 20 / 10min ≤ 120），超限返回 429 + Retry-After，保护下游 LLM/检索等昂贵调用。

B.5 多轮任务链

意图识别后，orchestrateTaskChain 按"活跃任务链"决定本轮真正执行哪个任务，可覆盖意图给出的 workflow。这让"推荐并下单"这类复合目标能跨多轮自动推进。

复合目标（规划）

TaskPlanningService 把"先推荐再加购再下单"拆成有序任务链（PLANNING → EXECUTING），逐轮取 next pending task 执行，路由随计划走。

原子目标

单一动作（如"查价格"）→ 单任务 EXECUTING 链，路由保持意图给出的 workflow。

每个子图执行完，build_answer_context 调 advanceTaskChain：成功标 SUCCEEDED 并追加执行明细 step，失败标 FAILED；无剩余 pending 任务则链收尾为 SUCCEEDED。链/任务状态持久化于 agent_context_items，由 TaskChainCoordinator 管理。元意图（澄清/闲聊/未知）不形成任务链。

B.7 混合检索内核

检索是 RAG 的心脏。本系统采用语义 + 关键词双路召回 → RRF 融合，并针对电商商品做了多项下推优化。

语义检索Milvus
ProductSemanticRagRetriever
↘
RRF 融合ProductRrfFusion
↗
关键词检索PostgreSQL
ProductKeywordRagRetriever
优化点实现价值
chunkType 下推按意图把召回限定到特定 chunkType，PREFERRED / FALLBACK 两阶段详情问题优先 ATTR/DESC，提升精度且不丢召回
标量过滤下推MilvusScalarFilterBuilder（Milvus 原生表达式）+ ProductPostgresFilterBuilder品牌/类目/价格在引擎侧过滤，减少回捞
词典归一BrandDictionaryService / CategoryDictionaryService把"苹果/Apple"等别名归一到标准品牌/类目
RRF 融合score += 1/(rrfK + rank + 1)无需调权即可稳健融合两路排名
代际对齐回查只取活跃代际 chunk杜绝半提交向量进入回答（见 A.7）
关键词路由PG 上 to_tsvector + plainto_tsquery，pg_trgm / ILIKE 兜底非 PG 环境也能退化运行

未启用 Milvus 时，仅关键词路生效，链路依旧可用（优雅降级）。

B.7+ 检索的降级与重试

检索对"部分可用"高度容忍：任一子能力（向量库 / 某一路 / LLM / 词典）退化，链路都尽力返回结果而非报错。在线检索请求内不重试——采用 fail-fast + 分层降级，把"重试"留给离线索引（见 A.9）。

分层降级

L1
分支级 · 双路并发 + 独立超时语义(Milvus) 与 关键词(PG) 并发执行，各自受 semanticTimeoutMillis / keywordTimeoutMillis 限时（CompletableFuture.orTimeout）。单路超时/异常 → 标 *_timeout / *_unavailable 并返回空，另一路结果照常融合；Milvus 未启用 → semantic_unavailable，纯关键词跑
L2
语义两阶段 · PREFERRED → FALLBACK先按 intent 下推精确 chunkType 检索；仅当 PREFERRED 零命中才用更宽的 chunkType 集合（buildFallback）重搜一次，先精后宽，兼顾精度与召回
L3
关键词场景级 · 多 searcher 并行FAQ / 营销 / 卖点 / 评价 evidence searcher 并行召回；单 searcher 失败独立降级，不拖累其它通道（KeywordRetrievalRouter 内逐路 catch）
L4
前置条件抽取兜底LLM 抽 ProductQueryCondition 失败 / 超时 / 非 JSON → 返回 empty 条件，退化为纯文本检索，绝不阻断主链路
L5
词典归一兜底品牌 / 类目词典加载或归一异常 → 跳过归一、按原词检索（BrandDictionaryService / CategoryDictionaryService）
∅
双路皆失败 / 零命中返回空上下文并标降级 → 答案转"没有完全匹配的商品"话术（见 B.10），仍给用户一个可读回复

降级可观测

每一次降级都会把原因写入 degradedNotes（如 semantic_timeout / keyword_unavailable / semantic_unavailable），随 ProductSearchResult 透传到 ProductQueryWorkflowResult.degradedNotes，并打结构化日志：product hybrid retrieval degraded / zero hit / unavailable。客户端与排障都能据此判断"这次回答是否在降级态下产出"。

degradedNotes 标记含义
semantic_timeout / keyword_timeout该路超时被放弃，结果仅来自另一路
semantic_unavailableMilvus 未启用或语义路异常，纯关键词召回
keyword_unavailable关键词路异常，仅语义召回
两者同时出现双路皆失败 → 空上下文 + log.error，答案走兜底话术

为什么请求内不重试

fail-fast 而非 retry

在线检索面向 SSE 实时回答：① 请求内重试会拉长首字延迟、破坏流式体验；② 反复打 LLM / 向量库会撞 RPM / TPM 限流，把局部故障放大成雪崩。因此每一路只给一次机会、超时即放弃，宁可降级也要快速给出结果。真正需要"重试到成功"的可靠性诉求，由离线索引链路承担（下表）。

#X1 并发模型

全局启用虚拟线程（spring.threads.virtual.enabled=true）。所有阻塞 I/O（JDBC / Milvus / Spring AI 调用）经 RagConcurrencyConfiguration.ragBlockingScheduler 隔离到虚拟线程承载；fire-and-forget 用 ragVirtualThreadExecutor。多路检索 query 经 WebFlux Flux.flatMap 并发。禁止新增固定大小线程池——既避免无谓占用，也防止撞模型 RPM 限流。

#X2 幂等与降级

幂等

  • 在线：requestId / turnId 贯穿一次回合，重复请求可识别
  • 离线：内容 shortSha + 索引代际，重复内容 SKIP
  • Outbox：消息重投靠代际/哈希收敛

降级

  • Milvus 关 → 仅关键词检索
  • RocketMQ 关 → 进程内索引
  • 答案 LLM 失败 → 规则兜底
  • 意图 LLM 失败 → clarify 兜底
  • 检索内部分层降级 → 见 B.7+

错误一律经 GlobalExceptionHandler 收口，对外白名单化文案，不泄漏堆栈与内部类名；SSE error 事件携带 recoverable 标记指导客户端是否可重试。
