1. 结论摘要

3-4 次 一次商品查询可能触发的 LLM 调用：主意图、任务规划、商品条件解析、最终答案生成。
N+1 商品 hydrate 当前逐个 getProduct，评价场景又逐个 listReviews。
已并发 keyword / semantic 双路召回已经并发，keyword 内部 evidence 也已经 fan-out 并发。
最优先处理的方向：先减少非必要 LLM 与重复 DB 往返，再补齐 SQL 索引和观测。对纯商品查询，建议优先绕过任务规划 LLM、允许规则答案直出、批量 hydrate catalog，这三项通常比继续调 RRF 权重更直接影响 P95。
优先级 优化项 主要收益 改造风险
P0 纯查询绕过任务规划 LLM 减少一次同步模型调用，降低平均延迟和模型成本 低，需要保留多步骤购买目标的规划入口
P0 最终答案支持规则直出开关 商品列表/对比结果已由 responseBuilder 生成，可省一次 answer LLM 中，需要确认体验文案要求
P0 真正应用 LLM timeout 保护 P99，避免用户请求被模型调用长时间挂住 低，中断和降级路径要测
P1 批量 hydrate 商品和评论 把 topK 商品详情从 2N 次 JDBC 往返降到 1-2 次 中，需要新增 facade 与 repository 查询
P1 补齐 catalog evidence 文本索引 稳定关键词路径，降低 review/FAQ/marketing 场景慢查询风险 中，需要生产库并发建索引与 explain 验证
P2 缓存/复用 Graph 编译结果 降低每请求固定 CPU 与对象分配成本 中，当前节点闭包捕获 eventSink，需要小重构

2. 当前查询链路

当前用户查询入口是 GuideAgentTurnController.turnStream，SSE API 为 GET /public/agent/turn。主链路经过会话、主意图路由、任务链调度、具体 workflow、答案生成和落库。

Client
  -> GuideAgentTurnController /public/agent/turn
  -> allocateTurnId + GuideGraphStreamService.turnStream
  -> per-request graphFactory.compile(...)
  -> check/init/load conversation context
  -> save user message
  -> main intent LLM
  -> task chain orchestration
       -> possible task planning LLM
  -> product_query_workflow
       -> condition parse LLM
       -> validate / merge previous condition / build filters
       -> ProductSearchSpiAdapter
            -> keyword branch in orchestration executor
                 -> profile / marketing / FAQ / review evidence parallel JDBC search
            -> semantic branch in bounded virtual-thread executor
                 -> Milvus search + PostgreSQL vectorId lookup
            -> RRF fusion + base rank
       -> ProductRanker hydrate catalog product/reviews
       -> post filter / comparison / responseBuilder
       -> persist product candidates, focus, last result
  -> build answer context
       -> possible answer LLM stream
  -> save assistant message
  -> completed SSE

3. 瓶颈扫描结果

P0 一次纯商品查询可能触发过多 LLM

主意图识别、任务规划、商品条件解析、最终答案生成都复用 intentChatClient。其中商品条件解析是核心必要步骤；主意图可通过规则/轻模型缓存优化；任务规划和最终答案生成对纯查询不是总必要。

  • MainIntentRouterService.route(...) 调用 intentChatClient.prompt(prompt).call().entity(...)。
  • GuideStateGraphFactory.startNewGoalChain 在 isPlanningWorthy(intent) 为 true 时调用 taskPlanningService.plan(...)，而 PRODUCT_SEARCH/PRODUCT_QUERY/PRODUCT_COMPARE 都被纳入 planning-worthy。
  • ProductQuerySubgraphFactory.pqTransformQuery 调用 llmService.parse(...) 将自然语言解析为结构化 condition。
  • GuideStateGraphFactory.buildAnswerContext 在成功时调用 tryStreamingLlmAnswer(...)，即使 product query 已经生成了 NODE_MESSAGE。

P0 LLM timeout 配置被读取但未真正应用

OpenAiClientConfiguration.intentChatClient 读取了 graph.agent.intent-llm.timeout，但当前只用于日志，未配置到底层 HTTP client 或模型调用 deadline。主意图、规划、条件解析、答案生成都复用这个 client，因此单个模型慢请求会放大整条链路 P99。

证据：src/main/java/com/bytedance/ai/infrastructure/config/OpenAiClientConfiguration.java:160 读取 timeout，:183 只记录日志。

P1 Catalog hydrate 存在 N+1 查询

ProductRanker.refine 对每个候选逐条调用 catalogQueryFacade.getProduct；getProduct 内部又查商品主表和 SKU；评论类场景还会逐个商品查 listReviews。

  • ProductRanker.java:73 遍历候选。
  • ProductRanker.java:85 逐个 hydrate reviews。
  • CatalogQueryService.java:45 getProduct 查询商品后再查 SKU。
  • CatalogQueryService.java:55 listReviews 单商品查询。

P1 Catalog evidence 文本索引不完整

关键词 evidence 搜索器会对 catalog_product_knowledge.content/title、catalog_product_faq.question/answer、catalog_product_review.content 做 to_tsvector(...) 与 LIKE '%query%'。schema 目前只有 catalog_product.title 的 FTS/trgm 索引，以及 SKU 的 jsonb_path_ops，未覆盖这些表达式。

证据：scripts/rag/pgsql/full_schema.sql:619 只给 product title 建 FTS/trgm；:680、:702、:730 只给 knowledge/faq/review 的 product_id 建索引。

P1 queryMode 未用于跳过不必要召回分支

ProductQueryCondition 已包含 queryMode，提示词也要求 LLM 输出 KEYWORD_ONLY | SEMANTIC_ONLY | HYBRID，但 ProductSearchSpiAdapter 当前总是提交 keyword 和 semantic 两路。精确型号、库存/价格过滤、上一轮评价追问等场景有机会只跑必要分支。

P2 调试日志处于 INFO 路径

ProductQueryDebugLogger 在 INFO 级别打印 slot、PG filter、Milvus filter、hydration 等多行调试日志。它对竞赛展示很有帮助，但在高 QPS 下会增加字符串构造、日志 IO 和存储成本。

证据：ProductQueryDebugLogger.java:49、:85、:91、:107。

P2 会话与任务链写入次数较多

每轮请求会同步分配 turn、检查/初始化会话、加载最近消息、保存用户消息、更新 turn、推进任务链、持久化候选/焦点/last result、保存 assistant 消息。正确性优先没有问题，但 P95 优化阶段应合并非必要写入，或把非阻塞型上下文持久化移到响应后异步执行。

4. 分阶段优化方案

P0 4.1 纯商品查询绕过任务规划 LLM

目标：对 PRODUCT_SEARCH、PRODUCT_QUERY、PRODUCT_DETAIL_QUERY、简单 PRODUCT_COMPARE 走单任务路径，只有用户明确表达“推荐并加入购物车”“搜索并下单”“买这个”等多步骤目标时才调用 planning LLM。

建议改法：

  • 新增 requiresPlanning(intent, targetWorkflow, message, writeAction)，替换当前纯枚举判断。
  • 只读 product query 默认返回 false；包含 加入购物车、下单、结算、购买 等动作，或主意图 writeAction=true 时返回 true。
  • 保留 taskPlanningService 失败后的单任务兜底。

验收：纯查询链路的 task_planning.call 计数降为 0；端到端 P95 至少减少一次模型调用耗时。

P0 4.2 商品查询结果默认规则直出，按需启用 answer LLM

目标：ProductQueryResponseBuilder 已经生成用户可读的列表、对比和澄清文案。对商品查询成功结果，可默认直接用 ProductQueryGraphStateKeys.NODE_MESSAGE，把 answer LLM 作为可配置增强。

建议配置：

graph.agent.answer-llm.enabled=true
graph.agent.answer-llm.product-query-mode=RULE_FIRST
# 可选值：RULE_ONLY / RULE_FIRST / LLM_ALWAYS

规则：列表/无命中/澄清用 RULE_ONLY；复杂对比或需要自然语言解释时可 RULE_FIRST，LLM 失败仍返回规则答案。

P0 4.3 为 LLM 调用设置真实 deadline

目标：把 graph.agent.intent-llm.timeout 从“日志字段”变成真实 HTTP read timeout 或调用层 timeout。

建议改法：

  • 为 OpenAiApi 使用带 connect/read timeout 的 RestClient 或底层 request factory。
  • 拆分 intentChatClient、productConditionChatClient、planningChatClient、answerChatClient，分别设置 maxTokens、timeout、retry。
  • 主意图和条件解析 timeout 建议 1.5s-3s；answer stream 可 8s-12s；planning 只在多步骤目标启用。

P1 4.4 批量 hydrate Catalog

目标：把 topK 商品 hydrate 从 N 次 getProduct + N 次 SKU + N 次 review，降为批量商品/SKU一次查询和批量评论一次查询。

接口建议：

interface CatalogQueryFacade {
    List<CatalogProductView> getProducts(List<Long> productIds);
    Map<Long, List<CatalogProductReviewView>> listReviewsBatch(List<Long> productIds, int perProductLimit);
}

SQL 建议：商品主表 WHERE id IN (:ids)；SKU WHERE product_id IN (:ids)；评论用 row_number() over(partition by product_id order by review_index, id) 实现每商品 limit。

P1 4.5 根据 queryMode 跳过召回分支

目标：利用 LLM 已输出的 queryMode 降低无效 Milvus/DB 调用。

queryMode 执行策略 适合场景
KEYWORD_ONLY 只跑 keyword，semantic 返回 completed empty 明确品牌/型号/价格/库存/精确字段查询
SEMANTIC_ONLY 只跑 semantic，保留 PG 二次校验 描述性需求、场景化推荐、开放语义
HYBRID 维持当前双路并发 默认策略和低置信召回

P2 4.6 缓存 Graph 编译结果

目标：避免每次请求重新构建 StateGraph 和子图。当前挑战是 GuideGraphNodeTemplate 在编译时捕获 per-request eventSink，因此不能简单把 CompiledGraph 作为 singleton。

建议路线：

  • 把 event sink 抽象为从 state 中读取的 request-scoped dispatcher，或使用可注入的 AgentStreamEventPublisher。
  • 将图结构编译成 singleton，运行时只传入 request state 和 correlationId。
  • 如果框架不支持动态 sink，至少缓存 StateGraph shape 或拆出子图 build 缓存，减少对象分配。

5. 数据库与索引建议

5.1 补齐 catalog evidence FTS/trgm 索引

当前 keyword searcher 会在 evidence 表上做 to_tsvector 和 lower(...) LIKE :likeQuery。建议用 CREATE INDEX CONCURRENTLY 在生产库分批上线，并配套 EXPLAIN (ANALYZE, BUFFERS) 验证。

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_knowledge_text_fts
  ON catalog_product_knowledge
  USING gin (to_tsvector('simple', coalesce(title, '') || ' ' || coalesce(content, '')));

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_knowledge_content_trgm
  ON catalog_product_knowledge
  USING gin (lower(coalesce(content, '')) gin_trgm_ops);

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_knowledge_title_trgm
  ON catalog_product_knowledge
  USING gin (lower(coalesce(title, '')) gin_trgm_ops);

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_faq_question_fts
  ON catalog_product_faq
  USING gin (to_tsvector('simple', coalesce(question, '')));

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_faq_answer_fts
  ON catalog_product_faq
  USING gin (to_tsvector('simple', coalesce(answer, '')));

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_faq_question_trgm
  ON catalog_product_faq
  USING gin (lower(coalesce(question, '')) gin_trgm_ops);

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_faq_answer_trgm
  ON catalog_product_faq
  USING gin (lower(coalesce(answer, '')) gin_trgm_ops);

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_review_content_fts
  ON catalog_product_review
  USING gin (to_tsvector('simple', coalesce(content, '')));

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_review_content_trgm
  ON catalog_product_review
  USING gin (lower(coalesce(content, '')) gin_trgm_ops);

5.2 SKU 与 active product 过滤索引

多个 SQL 使用 EXISTS (SELECT 1 FROM catalog_sku ... product_id = p.id AND status = 'ACTIVE')。建议补一个 partial/composite index：

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_sku_active_product
  ON catalog_sku (product_id)
  WHERE status = 'ACTIVE';

如果继续使用 lower(properties_json::text) LIKE 匹配容量/口味，jsonb_path_ops 不能直接支撑该表达式，可补：

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_catalog_sku_properties_text_trgm
  ON catalog_sku
  USING gin (lower(coalesce(properties_json::text, '')) gin_trgm_ops);

5.3 Milvus scalar 下推

RagProperties.Milvus.ProductSchema 已预留 status、stock、price、category、brand 等字段，但默认多数为空。建议离线索引补齐 Milvus metadata，并开启 scalar filter 字段，减少 vector candidates 和后续 PostgreSQL 二次过滤压力。

注意：Milvus schema 与索引数据必须同步演进，不能只改配置。先在影子 collection 验证召回质量和过滤正确性，再切线上 collection。

6. 观测与压测

6.1 指标缺口

当前 GuideGraphNodeTemplate 会记录节点耗时日志，product query 只对分支降级打了 counter。建议补 Micrometer timers 与 OpenTelemetry spans，按 runId/requestId/correlationId 串起来。

指标 标签 用途
agent_turn_duration intent, workflow, status 端到端 P50/P95/P99
agent_node_duration node, workflow, status 定位慢节点，如 main_intent、pq_rank、build_answer
llm_call_duration purpose, model, status, timeout 区分 intent / condition / planning / answer 成本
product_retrieval_branch_duration branch, queryMode, status keyword/semantic 分支耗时和降级率
catalog_hydration_duration mode, product_count, include_reviews 验证批量 hydrate 收益

6.2 基准压测建议

  1. 准备 30-50 条用户查询：精确商品、类目过滤、价格过滤、评价问答、对比、无命中、多轮 refine。
  2. 对每条记录：端到端耗时、首个 SSE 事件耗时、首个 answer delta 耗时、LLM 次数、JDBC 查询次数、Milvus 耗时、返回商品数。
  3. 分别测试 RAG_MILVUS_ENABLED=false 和 true；分别打开/关闭 answer LLM。
  4. 对慢 SQL 使用 EXPLAIN (ANALYZE, BUFFERS)，把计划保存到 docs/perf-explain/。
  5. 验收阈值建议：纯商品查询 P95 小于 2.5s；无 answer LLM 的规则直出 P95 小于 1.5s；错误/降级请求必须在 timeout budget 内返回。

7. 落地路线图

P0 快速止血 1-3 天 绕过纯查询 planning LLM；answer LLM 可配置；真实 LLM timeout；product debug 日志降级为 DEBUG 或开关控制。 纯商品查询 LLM 次数从 4 次降到 2 次以内；P95 明显下降；timeout 请求可降级返回。

P2 结构和观测 1-2 周 Graph 编译缓存重构；完整 Micrometer/OTel 指标；上下文写入合并或异步化；Milvus scalar schema 演进。 仪表盘能定位 P95 来源；固定成本降低；压测结果可回归比较。
建议先做的三个 PR：
  1. 在 GuideStateGraphFactory 中将纯只读 product intents 改为单任务，不调 planning LLM。
  2. 在 answer 阶段增加 product-query-mode=RULE_FIRST/RULE_ONLY 配置，并默认让列表/澄清/无命中规则直出。
  3. 为 CatalogQueryFacade 增加批量 hydrate 接口，替换 ProductRanker 的逐条查询。
