1总体结论

本仓库工程质量整体偏高（SQL 参数化、并发 / 事务、RAG 硬过滤、LLM 权限边界都做得相当扎实）。 核心判断：写操作（购物车 / 下单 / 库存）的业务正确性、并发安全、幂等性设计得很好，但所有 HTTP 接口完全没有身份认证， userId 由调用方在 query 参数里自报，且订单查询存在 IDOR——这意味着"防超卖 / 防重复下单"等护栏都在，却挡不住"冒充任意用户操作"。

最需要优先修复的 3 个问题（P0）

R1 · Critical

全局无认证 / 鉴权

无 Spring Security，userId / conversationId 为客户端自报 query 参数 → 任何人可冒充任意用户读写其购物车、结算、下单、读会话。

R2 · Critical

订单查询越权（IDOR）

GET /order/{id} 无归属校验，返回收货人姓名 / 电话 / 地址 → 遍历或猜测订单号即可批量拖取他人订单 PII。

R3 · High

管理 / RAG 写接口无鉴权

/admin/catalog/import* 与 /public/rag/documents 增 / 改 / 删 / reindex 全部无鉴权 → 目录篡改、RAG 投毒、文档删除。

3高风险（Critical / High）详细说明

Critical

R1 — 全局缺少认证 / 鉴权

触发路径
所有 /public/agent/turn、购物车、下单、会话接口；userId/conversationId 来自 GuideAgentTurnController.java:53-54 的 @RequestParam，透传至 ShoppingCartService.findOrCreate、OrderCommandService.createMockOrderFromContext。
攻击场景
攻击者 GET /public/agent/turn?userId=<受害者ID>&conversationId=<猜测>&message=结算购物车 即可操作他人购物车 / 触发其下单确认流程，或读取他人会话上下文。
为什么危险
所有"防超卖、乐观锁、下单幂等"护栏都假设 userId 可信；一旦可伪造，水平越权绕过全部业务隔离。
推荐修复
  • 接入认证（网关 JWT / Session / mTLS 皆可）；
  • userId 一律从已认证 principal 取，DTO 里的 userId 仅作比对或删除；
  • 所有按 userId 作用域的查询改为"认证用户作用域"。
建议测试
  • 用户 A 的 token 携带 userId=B → 期望 403；
  • 无 token 访问业务接口 → 期望 401；
  • A 只能命中自己的购物车（构造 B 的会话 ID 不应命中 B 的车）。
Critical

R2 — GET /order/{id} 越权读取订单 PII

触发路径
OrderController.getOrder → OrderService.getOrder → toView 返回 DeliveryAddressView（姓名 / 电话 / 省市区 / 详址）。
攻击场景
无需登录，遍历或猜测订单号即可拉取任意订单收货 PII。mock 订单号格式 ORD-yyyyMMdd-HHmmss-<6位hex>（OrderCommandService.nextOrderNo），时间前缀大幅缩小猜测空间。
为什么危险
直接的个人隐私（PII）泄露，且可规模化。
推荐修复
  • 校验订单归属当前认证用户后才返回；
  • 订单对外 ID 使用不可枚举值（UUID / 雪花 + 随机）；
  • 返回体按需脱敏（电话掩码）。
建议测试
A 请求 B 的订单号 → 403；未认证请求 → 401；订单号枚举脚本命中率应为 0。
High

R3 — admin 与 RAG 文档写接口无鉴权

触发路径
CatalogImportController 的 /admin/catalog/import、/json；RagDocumentController 的 create/update/del/reindex（路径前缀 /public，但执行删除 / 改写）。
攻击场景
  • 调 /admin/catalog/import 注入虚假商品并触发离线索引 → RAG 投毒，污染后续给用户的回答与推荐；
  • 调 DELETE /public/rag/documents/del/{id} 批量删除知识库；
  • 改写商品价格 / 库存元数据。
为什么危险
"admin"仅靠 URL 命名约定，无任何角色校验；RAG 投毒会让"看似可信"的导购回答携带攻击者内容。
推荐修复
/admin/* 强制管理员角色；文档写接口纳入认证；公开只读与受保护写分离；导入 / 删除加审计日志（已有部分 upload 审计日志，可扩展）。
建议测试
匿名调 /admin/catalog/import → 401/403；匿名 DELETE .../del/{id} → 401/403；普通用户 token 调 admin → 403。

4并发与事务专项检查

整体结论：这一块做得很好，是本仓库的亮点。

检查项结论证据
购物车 add/remove/update✅ 事务 + 乐观锁ShoppingCartService.transition：updateState(id, version, toState) 按 version 推进，并发命中 0 行抛冲突
库存扣减✅ 原子条件扣减，无超卖JdbcCatalogSkuRepository:84 / JdbcCatalogProductRepository:142：SET stock=stock-? WHERE ... AND stock>=?，按返回行数判断
创建订单✅ 事务内完成；唯一索引防重OrderService.placeOrder:107：uq_customer_order_cart_id 命中 DuplicateKeyException → 整单回滚（含已扣库存）
死锁规避✅ 统一锁顺序STOCK_LOCK_ORDER：按 (spuId,skuId) 升序扣减，消除 AB-BA 死锁
确认下单（mock 链路）✅ 条件状态机 + 快照校验OrderCommandService:75：WAITING_CONFIRMATION→CREATING 条件转移（重复确认返回失败）+ 购物车快照 hash 比对 + 过期校验 + 库存复核
重复请求 requestId 幂等⚠️ 见 R8requestId 未做幂等键；下单幂等由"购物车快照 + 唯一索引 / 状态转移"保证，但加购等写动作可被同 requestId 重放

设计点：加购（CartExecuteActionNode ADD）没有独立二次确认，仅下单有确认门。加购可逆、作用于本人车，属可接受，但建议在文档中明确"危险动作 = 下单 / 扣库存才需 human confirmation"的边界。

6已验证的安全点（通过项，供对账）

SQL 注入 / 拼接（B）— 未发现动态 SQL 全部用 ?/命名参数；FaqSearcher 的 String.format 仅插入白名单列名（question/answer），查询值绑定为命名参数；LIKE 经 escapeLike 转义；Milvus filter 仅由枚举名生成。
硬编码密钥（F）— 未发现Java 源零硬编码凭据；.env 已 gitignore 且未被 git 跟踪；.env.example 全为占位符；配置一律 ${ENV:default} 注入。
敏感信息日志（F/G）— 未发现明显泄露甚至有 ProductQueryConditionSanitizer 主动剔除 LLM 泄漏的 ID 型 token；查询 / 文件名日志多为 preview / 截断。
CORS（H）— 不存在过宽无任何 @CrossOrigin / 全局 CORS 配置 → 默认关闭。
Actuator（H）— 已收敛prod 仅暴露 health,info,metrics，show-details=never，loggers 只读。
文件上传校验（E）— 健壮大小上限 10MB、扩展名白名单、危险 content-type 拦截、路径穿越 cleanPath + 去目录、空字节注入检测（问题仅在该接口无鉴权，见 R3）。
500 响应 — 不外泄堆栈GlobalExceptionHandler 返回通用文案（关联 ID 缺失见 R9）。

7修复优先级

P0 · 必须马上修（上线即风险）
  • R1 接入认证，userId 取自 principal，停止信任客户端自报身份。
  • R2 GET /order/{id} 增加归属校验 + 不可枚举订单号。
  • R3 /admin/* 与 RAG 文档写 / 删接口加鉴权（管理员角色）。

R1/R2/R3 同源——本质是"补一层认证 + 资源归属校验"。建议作为一个安全基线一并落地。

P1 · 上线前必须修
  • R4 给公网 LLM 接口、上传、导入落地 @RateLimit（限流切面已就绪，只差注解）。
  • R6 默认 profile 改 prod 或缺失即 fail-fast，避免 dev 配置进生产。
  • R5 SSE 断连取消后台图执行（绑定 Flux 生命周期），抑制成本放大。
  • R8 用 requestId 为写操作补幂等键（与既有购物车 / 订单幂等互补）。
P2 · 后续优化
  • R7 输入侧 prompt 注入加固（分隔 / 标注不可信输入），会话记忆同理。
  • R9 统一在错误响应体回传 traceId/requestId。
  • R10 业务异常专用类型 + 面向用户文案。
  • R11 / R12 价格缺失过滤策略、上传文案一致性与大文件流式。
