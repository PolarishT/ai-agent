End-to-End Experience Guide

E2E 体验指南

面向评委的"一遍走通"手册：从启动服务、灌入商品数据，到与导购 Agent 多轮对话（推荐 → 筛选 → 对比 → 加购 → 下单），再到验收与排错。照着做，约 15 分钟即可完整体验离线 + 在线两条链路。

curl 即可体验 SSE 流式 多轮记忆 21 种意图

#0 体验全景

整个体验是一条直线：把商品变成知识库（离线），再用一句话把知识库变成导购回答（在线）。

配套文档

把服务跑起来 → 《部署文档》；想知道每一步底层怎么工作 → 《离线 / 在线链路技术文档》。本文只管"怎么体验"。

#1 准备

  1. 服务已就绪：按部署文档启动后，确认健康检查通过。
    shell
    curl -s http://localhost:8080/api/v1/actuator/health
# {"status":"UP"}
  2. 设个基础变量，后续命令复用：
    shell
    export BASE=http://localhost:8080/api/v1
  3. 工具：仅需 curl（带 -N 看 SSE 流）；psql 可选（做 SQL 级验收）；浏览器/Postman 亦可。
最省事的起步

不想配 Milvus / RocketMQ？在部署时把它们关掉即可——检索走关键词、索引走进程内，本指南所有场景依然能跑通，只是召回质量略降。

#2 灌入商品数据

真实工作流是「采集商品资料 → 落成 JSON 文件 → 导入」。这里用最贴近采集格式的 /admin/catalog/import/json（snake_case 字段）。一次导入会落库 商品 / SKU / 知识 / FAQ / 评价，并自动触发离线索引。

把一条商品资料保存成 catalog-bag-001.json（实际项目里通常由采集脚本产出）：

2.2 导入 JSON 文件

用 --data @文件名 把 JSON 文件作为请求体提交：

POST /admin/catalog/import/json
curl -s -X POST "$BASE/admin/catalog/import/json" \
  -H "Content-Type: application/json" \
  --data @catalog-bag-001.json

成功响应示例（message 会提示"已触发 RAG 离线索引"）：

200 OK
{ "success": true, "message": "商品已导入并触发 RAG 离线索引",
  "data": { "total": 1, "succeeded": 1, "failed": 0, "failures": [] } }

2.3 批量导入多个文件

对比 / 筛选场景需要多条商品。把每条商品各存成一个 JSON 文件（如 catalog-bag-002.json 超大旅行背包 349 元、catalog-bag-003.json 极简轻商务背包 159 元），循环导入：

shell
for f in catalog-bag-*.json; do
  curl -s -X POST "$BASE/admin/catalog/import/json" \
    -H "Content-Type: application/json" --data @"$f"; echo
done
另一种批量方式

若采集产物是「单个文件含多条商品」，可改用批量接口 POST /admin/catalog/import，文件内容为 {"items":[ … ]}（item 为 catalog 草稿格式，字段更全），同样用 --data @文件名 提交。

#3 验收离线索引

导入后索引是异步的，等几秒到状态变 INDEXED 即可。两种验收方式任选。

3.1 方式 A · 接口查进度

shell
# documentId 可从导入返回或文档列表获取；查作业当前态与状态时间线
curl -s "$BASE/public/rag/documents/index-job/1"
curl -s "$BASE/public/rag/documents/index-timeline/1"

3.2 方式 B · SQL 验收清单

#检查SQL预期
1商品主数据SELECT count(*) FROM catalog_product;≥ 导入数
2SKUSELECT count(*) FROM catalog_sku;≥ 商品数
3双写 RAG 文档SELECT count(*) FROM rag_documents WHERE source_type='catalog-spu';= 商品数
4索引完成SELECT status,count(*) FROM rag_documents GROUP BY status;全部 INDEXED
5切片分类SELECT metadata->>'chunkType', count(*) FROM rag_chunks GROUP BY 1;TITLE / DESC / ATTR 等均有
6属性抽取SELECT attributes_status,count(*) FROM catalog_product GROUP BY 1;DONE 为主（少量 FAILED 可接受）
卡住了？

状态长期停在 PENDING：多半是启用了 RocketMQ 但端点不通——查 rag_index_outbox 是否堆积，或临时把 RAG_ROCKETMQ_ENABLED=false 改走进程内。状态 FAILED 且报 dimension mismatch：embedding 维度 ≠ Milvus 维度（见部署文档 §4.3）。

#4 体验在线导购

核心来了。所有对话都打到同一个 SSE 入口：GET /public/agent/turn。

4.1 如何调用 SSE

用 curl -N 保持流不断开；中文参数用 -G --data-urlencode 自动编码：

shell
curl -N -G "$BASE/public/agent/turn" \
  --data-urlencode "userId=judge-001" \
  --data-urlencode "conversationId=demo-1" \
  --data-urlencode "message=推荐一款适合通勤的轻量双肩包"
多轮记忆的关键

同一段对话请保持 userId 与 conversationId 不变。这样"那个""第一个""再便宜点""结算购物车"才能联系上文。换一段新对话就换一个 conversationId。

4.2 看懂事件流

生产模式（默认）会按顺序吐出这些事件：

text/event-stream
event: turn.started      # 回合开始，开聊天气泡
event: workflow.started  # 意图已判定，进入对应业务子图
event: answer.delta      # 答案逐字流出（会有很多条）
event: answer.delta
event: answer.completed   # 答案落库完成
event: turn.completed    # 收尾：带 intent / targetWorkflow / status
事件客户端该做什么
turn.started打开一个 AI 回复气泡
workflow.started可显示"正在为你查找…"
answer.delta把 text 追加到气泡（打字机效果）
turn.completed关闭光标；可读取 intent 展示意图标签
error展示错误文案；看 recoverable 决定是否可重试

想看 Agent 内部"走了哪些节点"？加 streamMode=trace，详见 §6。

4.3 限流保护（@RateLimit）

导购对话每一轮都会触发意图识别、检索、答案生成等一连串昂贵调用，因此 /public/agent/turn 上加了注解式限流 @RateLimit，按「用户 + 会话」维度独立计数，保护下游 LLM 配额、防止单会话刷爆。正常逐轮体验不会触发。

项值
限流维度每个「userId + conversationId」独立计数
时间窗（与关系）1 分钟内 ≤ 20 次；10 分钟内 ≤ 120 次（任一窗口超限即拒绝）
超限响应HTTP 429 Too Many Requests + Retry-After 响应头（建议等待秒数）
实现common.ratelimit 模块的 AOP 切面，在方法执行前校验；SpEL key 求值失败会自动退化为方法级全局限流，不阻断链路
脚本连发可能触发

若用脚本对同一会话极快连发请求而收到 429，这是正常保护：读 Retry-After 秒数等待后重试，或换一个 conversationId 分摊。手动逐轮体验几乎不会碰到。

#5 对话剧本

下面是一段连贯的多轮对话（全程用 conversationId=demo-1），一口气体验推荐、筛选、对比、加购、下单的完整闭环；其后是覆盖全部意图的速查矩阵。

5.1 连贯多轮演示

把每条 message 依次发给 /public/agent/turn（同一 userId/conversationId）。右侧标注的是预期识别到的意图。

推荐一款适合通勤的轻量双肩包

为你推荐 NovaPack 轻量通勤双肩包：320g 机身、防泼水、独立 15.6 寸笔记本仓……（流式逐字输出，并附商品卡片）
→ product_query_workflow · 混合检索召回 + 实时价格回填
有没有 200 块以下的

→ 复用上文，价格区间下推过滤
这两个哪个更适合出差

#6 看 Agent 的"思考路径"

演示时最能体现工程含量的一招：用 streamMode=trace 把图节点事件全量打出来，直观看到 Agent 走了哪条路。

shell
curl -N -G "$BASE/public/agent/turn" \
  --data-urlencode "userId=judge-001" \
  --data-urlencode "conversationId=trace-1" \
  --data-urlencode "message=300以内的轻量双肩包对比一下" \
  --data-urlencode "streamMode=trace"

除了生产事件，你会额外看到每个节点的 node.started / node.completed：

trace 模式（节选）
node.started   check_conversation
node.completed load_conversation_context   # 装载多轮记忆
node.completed save_user_message
node.completed main_intent_router          # 判定 PRODUCT_COMPARE
node.started   product_query_workflow      # 进入商品子图
node.completed product_query_workflow      # 检索+对比完成
node.completed build_answer_context        # 流式答案
演示建议

给评委演示时，先用默认模式展示"丝滑流式回答"，再用 trace 模式展示"背后这套图编排"——一柔一刚，既有体验也有深度。

#7 验收与排错

现象可能原因处理
SSE 立刻断开 / 无事件未加 -N，或参数缺失被校验拒绝加 -N；确认 userId/conversationId/message 都传了
回答说"没有匹配的商品"还没导入数据 / 索引未完成先做 §2、§3，确认 INDEXED
意图识别成 CLARIFY话术太模糊或上下文不足说得具体些；保持同一 conversationId 延续上下文
收到 error + MAIN_INTENT_LLM_TIMEOUTLLM 超时recoverable=true，重发一次即可
收到 HTTP 429触发限流（同一会话发太快）按 Retry-After 秒数等待后重试，或换 conversationId（见 §4.3）
对比/筛选效果不明显商品太少多导入几条不同价格/规格的商品（§2）
"结算"没进下单流程表述不够明确用"结算购物车 / 提交购物车订单"等明确措辞
中文乱码未做 URL 编码用 -G --data-urlencode
